## 二、核心概念清单（每个都带「一句话结论 + 源码钉子」）

### 1. `struct pipe` 长什么样（`kernel/pipe.c:13`）

```c
struct pipe {
  struct spinlock lock;   // 保护下面四个字段的锁
  char data[PIPESIZE];    // 512 字节环形缓冲区
  uint nread;             // 已读字节总数
  uint nwrite;            // 已写字节总数
  int readopen;           // 读端是否还开着
  int writeopen;          // 写端是否还开着
};
```

一句话结论：**一条管道 = 一个缓冲区 + 读写计数 + 两端存活标志 + 一把锁**。
不变量：`nread == nwrite` ⇔ 缓冲区空；`nwrite == nread + PIPESIZE` ⇔ 缓冲区满。

### 2. `read` 返回 0（EOF）的唯一条件

> **当且仅当指向该管道写端的所有 fd 都被 close 后，再读才返回 0。**

源码钉子（`kernel/pipe.c:110`）：

```c
while(pi->nread == pi->nwrite && pi->writeopen){  // 空 且 写端还开着
  ...
  sleep(&pi->nread, &pi->lock);
}
```

`writeopen` 变 0 后，`while` 条件不成立，跳出后缓冲区为空 → 返回 0 = EOF。
`writeopen` 由 `close()` → `pipeclose()`（`kernel/pipe.c:59`）置 0。

完整因果链：

```
进程 close(写端fd)
  → 内核调 pipeclose → pi->writeopen = 0
  → wakeup(&pi->nread) 唤醒读者
  → 读者的 while 条件因 writeopen==0 而退出
  → read 返回 0
  → 用户程序 if(n==0) exit(0) 生效
```

### 3. fork 的系统调用链

```
user/usys.S（fork → SYS_fork 编号，执行 ecall）
      ↓
kernel/syscall.c（按编号查 syscalls[] 表，SYS_fork → sys_fork）
      ↓
kernel/sysproc.c:27  sys_fork()  →  return fork();
      ↓
kernel/proc.c:258    fork()  ← 真正的实现
```

> 注意：`ecall` 之后还有一层 trap 分发（trampoline.S 的 uservec → trap.c 的 usertrap → 才到 syscall），那是书第 4 章内容，Lab traps 再细啃。

### 4. `filedup` = 引用计数（不是「独享」）

源码钉子（`kernel/proc.c:287-289`）：

```c
// increment reference counts on open file descriptors.
for(i = 0; i < NOFILE; i++)
    if(p->ofile[i])
        np->ofile[i] = filedup(p->ofile[i]);
```

一句话结论：
- `filedup` 做的是 `f->ref++`，**让引用计数正确反映「还有几个 fd 表项指向这个文件」**；
- 如果只是 `np->ofile[i] = p->ofile[i]`（裸拷贝指针），父进程 close 时 `f->ref==0` 会 free 掉 `struct file`，子进程手里就变成**悬垂指针（use-after-free）** → 内核崩溃；
- 所以 `filedup` 解决的是**共享对象的生命周期管理**，而不是「让进程独享文件」——恰恰相反，fork 之后父子**共享同一底层 `struct file`**（共享 offset）。

### 5. 管道单向流动的机理

```
父进程的 p[1] fd  → struct file(写端) → struct pipe（同一份）
子进程的 p[1] fd  → 同一个 struct file(写端) → 同一个 struct pipe
```

`close(p[1])` 只关掉本进程自己的 fd 表项，`f->ref` 减 1，`struct file` 和 `struct pipe` 都还活着。字节写进 `struct pipe` 的 `data[]`，读端进程因为指向**同一个 `struct pipe`** 而能读到。

## 四、读源码方法论（5 步法）

> 心法：**先 grep 找位置，再 read 读细节；先读结构和接口，再读实现；一次只追一条主线，画成图。**

针对任意陌生代码库：

| 步骤 | 做什么 |
|---|---|
| ① 找地图 | 看 README + 目录结构 + 构建入口，弄清「分几层、每层干嘛」 |
| ② 找最小示例 | 找最简单的可运行程序，作为锚点 |
| ③ 读接口声明 | 读 `.h` 头文件（不读 `.c`），建立「有什么能力」 |
| ④ 顺一条主线追 | 挑一个具体问题，从「我调用它」追到「内核完成它」 |
| ⑤ 落地成图 | 读完画「调用链 + 数据流」图 |

**读单个内核函数的固定 5 问**：
1. 它操作什么数据？（先看 struct）
2. 谁调用它？（grep 往上追）
3. 它保护什么不变量？（看 acquire/release 括住哪个字段）
4. 它可能在哪 sleep / 被谁 wakeup？
5. 它和上下层怎么交接？（只看参数和返回值）

**grep 导航命令**：

```bash
grep -rn "pipealloc" kernel/    # 追调用方
grep -rn "sys_fork" kernel/     # 找系统调用实现
grep -n "struct file" kernel/file.h   # 找结构定义
```

## 五、xv6 / C 风格速查表

> 心法：**写的代码要和周围代码完全一致**，进新代码库先照抄已有 `.c` 文件的风格。

| 规则 | xv6 写法 | 反例 |
|---|---|---|
| 函数返回类型单独一行，`{` 单独一行 | `int`<br>`main(void)`<br>`{` | `int main(void){` |
| 控制流 `{` 跟在同一行 | `if(p){` | `if(p)`<br>`{` |
| 缩进 | 2 个空格 | 4 空格 / tab |
| `if/for/while` 与 `(` 无空格 | `if(x == 0)` | `if (x == 0)` |
| 二元运算符两侧有空格 | `n = read(fd, &x, 4)` | `n=read(fd,&x,4)` |
| 逗号后有空格，`(` 后 `)` 前无空格 | `read(fd, &x, 4)` | `read( fd , &x , 4 )` |

风格定位：K&R 直系 + 原版 Unix V6 风格（xv6 book 前言原话 *"xv6 loosely follows the structure and style of v6"*）。它不是当今某公司的主流标准（Linux 内核、BSD KNF 都不同），而是教学项目为清晰统一而定的习惯。
